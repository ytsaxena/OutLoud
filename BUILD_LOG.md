# OutLoud — Build Log

**Product:** OutLoud, an AI speaking coach for Indian job seekers who can read and write English but freeze when they have to speak it.
**Format:** Mobile web app, works in a phone browser on mobile data. Installable as a PWA.
**Build time:** one session for the original prototype (sections 1–6 below); several further sessions of iteration since (section 7).

---

## 1. What I built

A private mock-interview room. A female AI interviewer ("Priya") asks 3 questions out loud, the user answers out loud, and at the end they get a scorecard designed to keep a nervous person coming back.

| Requirement in the brief | How it is met |
|---|---|
| Onboarding | 3 steps: goal → level → permission primer. ~40 seconds. |
| Working practice session with a real AI API | 3 spoken questions generated by Gemini; user speaks; browser transcribes; Gemini evaluates. |
| User actually speaks (not typing / MCQ) | The only input in the session is the microphone. There is no keyboard anywhere in the room. |
| Some form of feedback | A 4-dimension scorecard, 3 specific wins, exactly one fix, a "say it better" rewrite, and objective stats. |
| A way to return and continue | Progress, streak (with a 7-day strip on the scorecard), session history and a score trend saved on the device; the next session's questions get harder. Optional Google sign-in for identity across a browser reinstall. |
| Mobile browser, mid-range Android, mobile data | No framework, no build step. Installable to the home screen (manifest + icons), so it opens like a native app with no browser chrome. |
| A voice that doesn't sound like a robot | Sarvam AI's Bulbul model generates Priya's speech server-side; falls back to the browser's built-in voice automatically if that call ever fails, so the app never breaks, it just sounds worse. |

---

## 2. Tools used

- **Claude (Cowork)** — planning, all of the code, the M3 design system, and the prompt engineering.
- **Google Gemini** (currently `gemini-3.5-flash-lite`, chosen for its higher free-tier rate limit) — question generation and answer evaluation, called through a Vercel serverless function.
- **Sarvam AI (Bulbul v3)** — Priya's natural Indian-English voice (`ritu`), called server-side so the key never reaches the client. Falls back to the Web Speech API automatically on any failure, including a quota running out.
- **Web Speech API** — `SpeechRecognition` for listening (device-only, audio never leaves the phone), `speechSynthesis` as the TTS fallback.
- **Firebase Authentication** — optional Google sign-in, identity only (no database yet — see §7).
- **Google Analytics 4** — funnel and event tracking; since this is a single-page app with no real navigation, screen transitions are sent as manual virtual page views.
- **Vercel** — static hosting plus serverless functions (`/api/interview`, `/api/tts`) to keep both API keys off the client.
- **Playwright + headless Chromium** — screenshotting every screen at 412×892 to check the layout without a phone in hand.

## 3. Architecture, and why

```
Android Chrome / iOS Safari
├── SpeechRecognition   ──► transcript (stays on the phone, audio is never uploaded)
├── fetch /api/interview ──► Vercel function ──► Gemini            (key in an env var)
├── fetch /api/tts       ──► Vercel function ──► Sarvam Bulbul v3  (key in an env var)
│                                                  │
│                                                  └─ on failure ─► speechSynthesis (fallback voice)
└── Firebase Auth (client SDK) ──► Google sign-in, identity only, no server round-trip
```

Two decisions that shaped everything else:

**Browser STT instead of an audio-streaming API.** It costs nothing per minute, adds no upload on a 3G connection, and it lets the product make a claim that actually matters to this user: *your voice never leaves your phone*. That line is in onboarding, in the permission primer, and on the landing screen, because the fear of being heard is the real barrier — not the technology.

**Exactly two Gemini calls per session, not one per question.** Questions are generated up-front while Priya is greeting the user, and evaluation happens once at the end over the whole transcript. On a slow connection the user never waits mid-interview, and the cost per session stays around a tenth of a paisa.

## 4. What broke, and the workaround

**The interviewer's voice was male on half the devices.**
`speechSynthesis.getVoices()` returns a different list on every Android build, and the default is often male. Fixed with a scoring function that ranks voices by name pattern (female markers, and a penalty for male ones) and by locale (`en-IN` > `en-GB` > `en-*`), then picks the winner. It also has to wait for the `voiceschanged` event, because the list is empty on first load in Chrome.

**Android Chrome refused to speak at all on the first question.**
Speech synthesis needs a user gesture before it will work. Since Priya speaks first, there had been no gesture yet. Worked around by speaking a silent, zero-volume utterance inside the "Allow and start interview" tap, which unlocks the audio channel for the rest of the session.

**`SpeechRecognition` kept stopping by itself mid-answer.**
Chrome ends a recognition session after a few seconds of silence, which for a nervous user thinking about their answer is fatal — it cut people off mid-sentence. Fixed by restarting recognition inside `onend` while the answer is still open, swallowing `no-speech` errors instead of treating them as failures, and using an explicit 3.5-second silence timer with a 4-second minimum, so a long thinking pause never ends the answer.

**`onend` never fires on some Android WebViews**, leaving the interview stuck with Priya silent forever. Every `Voice.say()` now carries a timeout guard sized to the text length, so the flow always advances.

**Speech recognition mangles Indian names and technical words.**
This is unfixable at the transcription layer, so it was handled at the prompt layer instead: the evaluation prompt tells the model the transcript comes from imperfect phone recognition and that a garbled word should be assumed correct. The raw transcript is also never shown back to the user as "what you got wrong" — it is only used for coaching.

**Early feedback drafts were demoralising.**
The first version of the scorecard led with mistakes and scored a real answer at 38/100. For a user who is one bad comment away from deleting the app, that is a product failure, not honest feedback. The prompt now hard-forbids any mention of accent or pronunciation, requires a win before any criticism, allows exactly one improvement, and the server clamps every score to a floor of 40.

**The API can fail, and the session must not.**
There is a complete offline path: a local question bank of 9 questions per goal across 3 difficulty levels, and a locally-computed scorecard built from word count, words-per-minute, filler-word count and longest answer. If Gemini times out at 25 seconds, the user still gets a real scorecard and never sees an error screen. Which path was used is logged (`feedback_ai` vs `feedback_fallback`).

## 5. Metrics instrumented

Every event is written to `localStorage` and visible in-app on the home screen (the chart icon, top right).

| Metric | Definition |
|---|---|
| **North Star** — Week 4 practice completion | % of signups completing ≥1 session during their 4th week. Target 40%. Needs 28 days of data. |
| Mic permission grant rate | Leading indicator #1. The first real gate. |
| Activation | % who speak at least one full answer on their first visit. |
| Session completion | % of started sessions that reach the scorecard. |
| D1 / D4 / D11 return | Return visits on the days the brief calls out. |
| Words spoken per session | The honest proxy for how much practice actually happened. |
| Average score trend | Whether people are getting better, which is what makes them stay. |

**Qualitative signal collected weekly:** one question after the scorecard — *"Do you feel more ready to speak English out loud than last week?"* — plus the raw transcripts of the first and latest session for the same user, read side by side.

**Drop-off hypothesis:** the biggest loss is between opening the app and the first spoken word. Two things stack there — granting the microphone, and the silence right after Priya finishes her first question, where a nervous person has to speak into a phone with nobody to blame if it goes badly. The second-biggest loss is Day 2, because nothing external pulls them back.

**Next experiment if retention is weak:** move the first success before the first friction. Add a 10-second "say your name out loud" warm-up that runs *before* the permission request is framed as an interview, so the user has already spoken English into the app once before they ever face a question. Measure activation rate against the current flow.

## 6. Known limitations (as of the original build)

- `SpeechRecognition` is Chrome/Safari only. Firefox Android users get a clear message rather than a broken screen; a recorded-audio fallback is the next thing to build.
- Progress is stored per-device, so there are no cross-device accounts and the Week 4 metric can only be measured for users who keep the same phone and browser. *(Partly addressed in §7 — Google sign-in now exists, but it's identity-only; progress still doesn't sync.)*
- The interviewer photo is a stock-style image with an invented name. If this ever ships beyond a prototype, it needs to be clearly labelled as an AI character so nobody believes they are talking to a real recruiter. *(Addressed in §7 — Priya is now labelled "AI Coach", not "AI interviewer".)*
- The scorecard's "say it better" rewrite is generated, not verified. It is good coaching, not certified English instruction.

## 7. Post-launch iteration

The prototype above shipped, then went through several rounds of real debugging, a full visual redesign, and three new integrations (voice, sign-in, analytics). This section is the same "what broke, and the workaround" format as §4, because that's where the actual engineering was.

### 7.1 Natural voice (Sarvam AI)

The browser's built-in `speechSynthesis` voice sounds robotic and varies wildly by device. Sarvam's Bulbul model gives Priya one consistent, natural Indian-English voice (`ritu`, tuned to a slower pace and lower temperature after the first pick sounded too sharp) — but getting it working reliably surfaced a run of real bugs:

- **`bulbul:v2` got deprecated mid-project** on new accounts; switched to `v3`, which also dropped `pitch`/`loudness`/`enable_preprocessing` params `v2` had.
- **AI Studio's `AQ.`-prefixed keys aren't `AIza`-prefixed**, and the proxy was routing them through `Authorization: Bearer`, which Sarvam rejects (`401 API_KEY_SERVICE_BLOCKED`) — both key formats actually need `x-goog-api-key`.
- **Mobile audio unlock was the wrong trick.** The original "play a silent utterance on first tap" pattern (borrowed from `speechSynthesis`) doesn't transfer to an `<audio>` element — playing an *empty, srcless* element doesn't register as real activation on strict mobile browsers (notably iOS Safari). Fixed by unlocking with a real, if near-silent, 1-sample WAV clip.
- **No cancellation.** `Voice.say()` originally had no way to invalidate itself — every call's fetch-then-play chain would eventually try to play, even if a newer call (or a skip) had already superseded it, so tapping through questions quickly could layer multiple lines of audio on top of each other. Fixed with a generation counter (`Voice.gen`) that any in-flight call checks before touching playback.
- **Graceful degradation was worth building deliberately, and it paid off**: Sarvam's free tier ran out mid-project (`402 insufficient_quota_error`), live, in front of a real user question about exactly this scenario — and the app kept working, silently falling back to the browser voice, no broken screen. Confirmed live, not just in theory.
- **Pre-fetching**: the next question's audio (or the closing line, on Q3) now starts fetching the moment the user begins *answering* the current one, so the transition has no perceptible delay. The 4 fixed acknowledgment lines are pre-warmed once per session too — trimmed down to just the 2 that are structurally reachable in a 3-question session, after noticing the other 2 were being fetched and thrown away unused on every session (wasted ~10% of the Sarvam characters billed per session for nothing).

### 7.2 Visual redesign

The original purple Material 3 theme was replaced end to end with a forest-green-and-cream palette (chosen from a set of options generated and reviewed side by side), plus:

- A manual light/dark toggle (persisted, applied before first paint to avoid a flash of the wrong theme) — the app previously only followed the OS setting.
- Every icon in the app went through two iterations: flat outline → emoji (for a "3D, modern" look) → back to vector SVG (emoji read as inconsistent across platforms and not "vector" per explicit feedback), landing on bold filled glyphs plus a shared CSS gloss treatment (radial highlight + inset shadow) for a glassy, dimensional feel without any image assets.
- The score screen became the visual centerpiece: a circular progress ring replaced the flat number, stats became an asymmetric "bento" layout instead of 4 equal boxes, and a 7-day streak strip was added so a completed session immediately shows where it fits in a habit, not just a one-off score.

### 7.3 Google sign-in (Firebase)

Added as identity-only (no database) — "Continue with Google" or "Continue as guest," with guest untouched from before. The interesting bug was the auth flow itself:

- **Redirect-based sign-in silently failed** (`auth/configuration-not-found`, then after fixing that, no error at all — just landing back on the same screen). Root cause: `signInWithRedirect` needs Firebase's `authDomain` (`*.firebaseapp.com`) to hand the result back to the app's actual domain (`out-loud-mu.vercel.app`) via storage shared across those two different origins — which modern mobile browsers' storage partitioning blocks. Switched to `signInWithPopup`, which communicates via `postMessage` between windows instead of shared storage, sidestepping the problem entirely. (The popup was originally avoided over a fear of mobile popup-blockers; that fear turned out to apply to automated test clicks, not real user taps — a real tap is not blocked.)
- **The welcome screen didn't know it was already signed in.** Pressing "back" to step 1 after signing in re-showed "Continue with Google," which looks like the session was lost even though Firebase's own session persists regardless of which screen is showing. Fixed by having the welcome screen read `Auth.user` and switch to "Continue as [name]" + a "sign out" link when applicable.

### 7.4 Analytics (GA4)

Standard `gtag.js`, plus one non-standard piece: since this is a single-page app, GA4's automatic page-view tracking only ever fires once, on load. `Nav.go()` now sends a manual virtual `page_view` on every screen change, so the funnel (welcome → goal → level → permissions → room → score → home) is actually visible in "Pages and screens," including where people drop off.

### 7.5 The skip/repeat race conditions — the real debugging story

By far the most time went here. The interview flow is a chain of `async` functions (`ask` → `listen` → `answered` → `ask` again, or `endSession`) connected by `await`s on TTS/STT calls that take real time — and "skip" or "repeat" needs to be able to interrupt that chain at any point. Each fix here exposed a slightly different version of the same underlying problem:

- **Skipping didn't stop the mic cleanly** — it just called `Ears.stop()`, which (correctly) fired the normal "answer received" callback with whatever partial audio had been captured, so a skip could be misread as a garbled answer and trigger an unwanted "I could not hear you clearly" prompt. Fixed by nulling the pending callback before stopping.
- **Guarding against a stale continuation by comparing the question index doesn't work in general.** The first fix compared `this.idx` before letting an `await`-resumed function proceed — correct when skip *advances* the index, but `repeatQ()` re-asks the *same* index, and `endSession()` never touches the index at all. Both cases let a stale callback's idx check trivially "pass," which is how the app ended up: speaking a closing line after the user had already reached the score screen, rendering the score screen twice (and double-billing the Gemini evaluate call), and — the one a real user actually caught — **recording 4 answers for a 3-question session**, because an old, orphaned listen cycle and a new one (started by a repeat) could both independently capture and push an answer.

  The real fix: replaced every idx comparison with a single generation counter (`askGen`), bumped by *anything* that should invalidate whatever's in flight — `ask()`, `skipQ()`, `repeatQ()`, `quit()` — checked at every resume point. A mismatch always means "superseded," independent of whether the index happens to match.
- **A second, cheaper backstop was added on top anyway**: both places that push to the answers array now hard-refuse to add a 4th entry, full stop, and the feedback screen separately caps its render to 3 — not because the root-cause fix isn't trusted, but because a hard structural invariant is worth more than one more patched edge case, especially for something a real user will notice immediately.
- **Skip/repeat tapped before the questions had even loaded** pushed a phantom answer referencing `undefined` question text, inflating the count before any real question existed. Fixed by disabling (and visually dimming, with an explanatory note) both buttons until `this.qs` is actually populated.
- **A completely separate mic bug, same symptom class ("not listening"):** the camera-preview `getUserMedia` call requests `{audio: true, video: ...}` to bundle mic + camera into one permission prompt, but that audio track was never actually used for anything — and leaving it open for the whole session holds the microphone hardware on Android Chrome, blocking the *separate* system speech-recognition engine from claiming it ("Speech Recognition and Synthesis from Google cannot record now..."). Fixed by stopping just the audio track immediately after permission is granted, keeping the video track alive for the self-cam preview.

### 7.6 Smaller fixes worth recording

- The live transcript box carried the *previous* session's last spoken answer into the first few seconds of a new one — `beginSession()` reset the caption but not the transcript.
- "Say it better" only ever showed one rewrite (Gemini's choice of the single most improvable answer); it now shows one per question, with skipped questions honestly labelled "You skipped this question" instead of showing a fabricated example answer attributed to the user.
- Added a PWA manifest, home-screen icons, and Open Graph/Twitter card meta tags so the link is shareable and installable — none of that existed in the original build.

## 8. Updated known limitations

- No cross-device sync. Google sign-in exists but is identity-only; progress and streaks are still per-device `localStorage`. The obvious next step if this keeps going is Firestore.
- No rate limiting on `/api/interview` or `/api/tts`. Fine for friends-and-family sharing; a script hitting those URLs directly (not through the UI) could run up the Gemini/Sarvam bill before anyone noticed.
- No push notifications for streak reminders — deliberately deferred, since a real version needs a service worker, push subscriptions, a database, and a scheduled job, not a quick add.
- Sarvam's free tier is small relative to real multi-user traffic; budget for topping it up more than once. The app degrades gracefully when it runs out (confirmed live), it just sounds worse.
